# تقرير تحليل ومواءمة نظام المحاسبة

**المرجع الأساسي للتصميم:** ملف شرح نظام الأونكس المرفق من المستخدم. تم التعامل مع الشاشات الحالية باعتبارها واجهات WPF يجب الحفاظ على شكلها، بينما تم تعديل الطبقات الخلفية ومخطط البيانات لتقترب من دورة الأونكس: تهيئة الشركة والفروع، السنة والفترة المالية، دليل الحسابات الهرمي، مراكز التكلفة، المستندات التشغيلية، المخزون بالدفعات، القيود اليومية، ونقطة البيع.

## النتيجة التنفيذية

تم إنشاء نسخة عمل معدلة في مجلد `modified`. الواجهات الحالية لم تُعاد صياغتها بصريًا؛ الإصلاحات ركزت على النماذج والخدمات وطبقة الوصول إلى البيانات ودورة المستندات. أضيف مخطط SQL موحد في `Database/01_OnyxAlignedSchema.sql`، وتم توحيد الاتصال في `DbConnectionFactory.cs` مع إبقاء إعداد الاتصال بسيطًا وقابلًا للتعديل من `App.config` كما طلب المستخدم، من دون إدخال نظام أمني ثقيل أو بنية صلاحيات معقدة.

| المجال | حالة المواءمة | أهم التغيير |
|---|---|---|
| سياق المستخدم | منجز | الشركة والفرع والسنة والفترة والعملة أصبحت جزءًا من `UserSession`. |
| دليل الحسابات | منجز | الاعتماد على `GL_Accounts` وشجرة الأب/الابن ومنع الحركات على الحساب غير القابل للترحيل. |
| القيود اليومية | منجز جزئيًا | توحيد الرأس والتفاصيل، التحقق من توازن المدين والدائن، والاعتماد على TVP وإجراء حفظ ذري. |
| السنة والفترات | منجز | تحويل شاشة الفترات إلى `GL_FiscalYears` و`GL_FiscalPeriods` ومنع الحفظ في فترة مغلقة. |
| المشتريات | منجز جزئيًا | فاتورة، تفاصيل، دفعة، حركة إدخال مخزنية، وتحديث رصيد المورد داخل معاملة واحدة. |
| المخزون | منجز | اعتماد `ItemBatches` وحركة المخزون والفرع، مع التحقق من الكمية وحد الصلاحية. |
| نقطة البيع | منجز جزئيًا | وردية، فاتورة بيع، تخصيص FIFO للدفعات، حركة إخراج مخزنية، وتحديث رصيد الوردية. |
| الفواتير المعلقة | منجز | مواءمة `PendingInvoices` و`PendingInvoiceDetails` مع الحذف المتسلسل. |
| العملات والأصناف | منجز | توحيد الحقول التي تعتمد عليها شاشات WPF مع الجداول المرجعية. |
| الإغلاق الأمني | مقصود أن يبقى بسيطًا | لم تتم إضافة تشفير أو Identity أو خدمة صلاحيات مركزية جديدة؛ تم الاكتفاء بالاتصال من الإعدادات والتحقق التشغيلي. |

## الأخطاء البنيوية التي عولجت

كان المشروع يستخدم أكثر من تمثيل لدليل الحسابات، مع وجود مراجع إلى جدول حسابات قديم وحقول مثل `IsSubAccount` لا تنسجم مع قاعدة الترحيل. تم توحيد المستودع والخدمات والشاشات على `GL_Accounts`، وأصبح الحساب الرئيسي غير قابل للحركة عندما تكون قيمة `IsPostable` غير مفعلة. كما تم منع حذف الحساب المرتبط بحركات أو بحسابات أبناء بدل حذف يترك قيودًا أجنبية مكسورة.

كانت طبقة القيود تستدعي إجراءً مخزنًا لا يطابق نموذج التفاصيل في بعض النسخ، وكان من الممكن حفظ قيد غير متوازن أو على حساب رئيسي. تم توحيد `VoucherHeader` و`VoucherDetail`، وإضافة التحقق من تساوي إجمالي المدين والدائن قبل الحفظ، وربط التفاصيل بالـTVP `dbo.GL_VoucherDetailType` والإجراء `dbo.sp_GL_Vouchers_Save`.

كانت دورة المخزون تعتمد أحيانًا على كمية في جدول الصنف فقط، وأحيانًا على دفعات بأسماء مختلفة مثل `BatchNo` و`BatchNumber`. تم اعتماد `ItemBatches` كمصدر لتخصيص الكمية، و`InventoryMovements` كسجل حركة، مع الاحتفاظ برصيد `Items.StockQuantity` للتوافق مع الشاشات الحالية. في البيع السريع يتم اختيار الدفعة الأقرب انتهاءً أولًا، ثم يتم إدخال تفاصيل البيع وحركة الإخراج وتحديث الرصيد داخل معاملة واحدة.

كانت بعض الشاشات تحمل اسم جهاز المطور داخل سلسلة الاتصال. تم استبدال هذه السلاسل بمصنع اتصال واحد يقرأ `DefaultConnection` من `App.config`، وبالتالي لا يرتبط المشروع بجهاز بعينه. كما تم تصحيح شاشة إغلاق الوردية لتستخدم `CashSales` و`CardSales` و`ReturnsAmount` و`DifferenceAmount`، وهي الأسماء الموجودة في المخطط الجديد.

## مخطط قاعدة البيانات المقترح

المخطط في `Database/01_OnyxAlignedSchema.sql` يحافظ على أسماء رئيسية مستخدمة في الواجهات، لكنه يربطها ضمن دورة أوضح:

| المجموعة | الجداول الأساسية | العلاقة التصميمية |
|---|---|---|
| التهيئة | `System_Companies`, `System_Branches`, `System_Currencies` | الشركة تملك فروعًا، والشركة تحدد عملة الأساس. |
| الزمن المحاسبي | `GL_FiscalYears`, `GL_FiscalPeriods` | السنة تملك فترات، والمستند والقيد يرتبطان بهما. |
| الدليل | `GL_Accounts`, `CostCenters` | الحسابات هرمية، ومركز التكلفة اختياري على سطر القيد. |
| القيود | `GL_VouchersHeader`, `GL_VoucherDetails`, `GL_VoucherSequences` | رأس واحد لعدة أسطر، مع رقم تسلسلي بحسب الشركة والفرع والسنة ونوع القيد. |
| المخزون | `Items`, `ItemBatches`, `InventoryMovements` | الصنف يملك دفعات، وكل إدخال أو إخراج يسجل حركة مصدرية. |
| الشراء | `PurchaseInvoices`, `PurchaseInvoiceDetails`, `Suppliers` | الفاتورة ترتبط بالمورد وبالفترة، والتفاصيل تنشئ دفعات وحركة إدخال. |
| البيع | `SalesInvoices`, `SalesInvoiceDetails`, `Customers`, `Shifts` | الفاتورة ترتبط بالفرع والفترة والوردية، والتفاصيل تخصم من الدفعات. |
| المعلّق | `PendingInvoices`, `PendingInvoiceDetails` | رأس الفاتورة المعلقة يحوي تفاصيلها، والحذف يتم تلقائيًا بالتفاصيل. |

تم أيضًا تصحيح بيانات التهيئة بحيث لا تفترض أن `CompanyID` أو `FiscalYearID` أو `BranchID` تساوي الرقم 1. يتم الحصول على المعرفات من الأكواد الفعلية بعد الإدراج، وهذا يمنع فشل التهيئة عند تشغيلها على قاعدة موجودة مسبقًا.

## ما لم يتم اعتباره مكتملًا

لا يمكن اعتبار الترحيل المحاسبي التلقائي للمبيعات والمشتريات مكتملًا بصورة مهنية قبل تحديد أكواد حسابات المخزون والمبيعات وتكلفة المبيعات والصندوق أو البنك وحساب المورد والعميل داخل إعدادات الشركة. النسخة الحالية تسجل المستند والحركة المخزنية وتترك `IsPosted` على حالته المناسبة إلى أن يتم اختيار هذه الحسابات. هذا مقصود لمنع إنشاء قيود بأكواد افتراضية خاطئة.

كما أن المشروع يستهدف **.NET Framework 4.7.2 وWPF**، ولم تتوفر في بيئة التحليل أداة Windows MSBuild أو SQL Server محليًا؛ لذلك تم إجراء فحص XML، وفحص أحداث XAML، وفحص العقود بين الكود والمخطط، وفحص الاتصالات الصلبة. يجب تنفيذ التجميع النهائي واختبار SQL على جهاز Windows يحتوي Visual Studio أو Build Tools وSQL Server.

## نتائج التحقق

تم تشغيل فاحص التكامل على الملفات المعدلة وكانت النتيجة `errors: 0` و`warnings: 0`. كما أظهر فحص البنية أن XML صالح، ولا توجد أحداث XAML غير مرتبطة، ولا توجد سلاسل اتصال تشير إلى جهاز المطور خارج مصنع الاتصال المركزي. نتيجة فحص البنية القديمة التي تظهر `legacy_purchase_columns` هي تنبيه نمطي غير دقيق لأن `BatchNumber` موجود فعلًا في `PurchaseInvoiceDetails` حسب المخطط، بينما `BatchNo` هو اسم عمود جدول `ItemBatches`.

## طريقة التشغيل على جهاز Windows

يجب نسخ مجلد `modified` إلى جهاز Windows ثم فتح `accounting_project.csproj` في Visual Studio 2022 مع تثبيت workload الخاص بتطبيقات سطح المكتب .NET. بعد إنشاء قاعدة SQL Server فارغة، يتم تعديل `DefaultConnection` في `App.config` ثم تشغيل ملف `Database/01_OnyxAlignedSchema.sql` مرة واحدة على قاعدة البيانات. بعد ذلك يتم فتح الشركة والفرع والسنة والفترات، ثم دليل الحسابات، ثم الأصناف والدفعات، قبل تجربة الشراء أو البيع.

لا يُنصح بتجربة البيع السريع قبل إنشاء فترة مالية مفتوحة تغطي تاريخ اليوم، وإضافة دفعة للصنف في الفرع، والتأكد من أن `Items.StockQuantity` متوافق مع مجموع الدفعات. هذا الشرط يحمي من ظهور رصيد بيع لا يقابله مخزون فعلي.
